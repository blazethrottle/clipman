서명된 터널로 흐르는 다운로드 프록시

cobalt는 영상을 저장하지도 편집하지도 않습니다. 원본을 짧은 수명의 서명 URL로 감싸 그대로 흘려보내는 스트리밍 프록시입니다. 이 구조가 clipman이 무엇을 따라가고 무엇을 버려야 하는지를 정확히 알려줍니다.

01

한눈에 보는 실체

cobalt의 정체성은 세 문장으로 압축됩니다. 이 셋이 나머지 모든 설계를 결정합니다.

  • 다운로드는 하지만 편집은 없다. 요청 스키마가 .strict()로 닫혀 있고 시작·끝·구간 같은 시간 파라미터가 전혀 없습니다. 클리핑 기능은 draft PR로 진행 중이나 "비효율적이고 로컬 처리와 UI가 미비하다"는 이유로 아직 병합되지 않았습니다.
  • 원본을 저장하지 않는다. 서버에 남는 것은 영상이 아니라 90초짜리 암호화된 스트림 메타데이터뿐입니다. README의 "캐시 없는 프록시"라는 서술은 코드와 일치합니다.
  • 프론트엔드와 처리 백엔드가 분리된다. 웹 UI(web)는 정적 사이트이고, 실제 다운로드 처리(api)는 별도 인스턴스입니다. 사용자는 웹은 공식 것을 쓰면서 처리 인스턴스만 자기 것으로 바꿀 수 있습니다.

핵심 대비

cobalt = 다운로드 프록시. clipman = 다운로드 + 편집 도구. cobalt가 하지 않는 바로 그 "편집"이 clipman의 존재 이유이자 난이도의 대부분입니다. 벤치마크는 다운로드 절반만 알려줄 뿐, 나머지 절반은 clipman이 새로 설계해야 합니다.

서비스 추출 로직을 플랫폼당 한 파일로 두고, processing/match.js가 라우팅하는 플러그인식 구조입니다.

테스트 전략 (참고)

cobalt의 테스트는 사실상 하나입니다. 21개 추출기를 실제 서비스 대상으로 돌려 "올바른 응답 상태(tunnel/redirect/error)를 반환하는가"만 확인하는 통합 테스트입니다(api/src/util/test.js + GitHub Actions matrix). 실제 다운로드 바이트 검증은 // TODO: stream testing으로 비어 있고, 웹 UI 테스트는 아예 없습니다(타입 체크만). 플랫폼이 API를 바꾸면 CI가 잡아내는, 미디어 추출 도구에 최적화된 회귀 방어 방식입니다.

03

04

미디어 처리 내부

cobalt가 영상에 손대는 정도는 최소한입니다. 비디오는 거의 항상 재인코딩 없이 컨테이너만 바꾸고, 실제 인코딩은 오디오 변환과 gif에서만 일어납니다. 전 과정이 디스크를 거치지 않는 스트리밍입니다.

proxy 원본 그대로

undici로 원본을 열어 그대로 pipe. 재인코딩·remux 없음. 클라이언트 Range 헤더를 원본에 그대로 전달해 구간 요청도 통과.

remux / merge 컨테이너만

ffmpeg로 처리하되 비디오는 항상 -c:v copy(무재인코딩). merge는 분리된 영상·음성 스트림을 -map으로 합침. mp4는 faststart 적용.

audio / gif 실제 인코딩

오디오 포맷·비트레이트 변환과 gif 팔레트 렌더링에서만 진짜 인코딩. gif가 가장 무거움.

local-processing 브라우저로 위임

서버 부하가 큰 처리를 클라이언트로 넘김. 브라우저는 libav.js(ffmpeg의 WASM 빌드)를 Web Worker에서 돌려 remux·transcode 수행, 결과는 OPFS에 저장.

ffmpeg 바이너리는 npm 패키지 ffmpeg-static으로 번들됩니다(별도 설치 불필요). 입력은 임시 파일이 아니라 내부 터널 URL이고 출력은 파이프(pipe:3)라, 결과물이 서버 디스크에 절대 쓰이지 않습니다. 대용량도 8MB 청크 제너레이터로 흘려 상수에 가까운 메모리로 처리합니다.

# remux (컨테이너 재포장, 무재인코딩) 개념
ffmpeg -i <video-tunnel> -i <audio-tunnel> \
  -map 0:v -c:v copy  -map 1:a -c:a copy \
  -movflags +faststart+frag_keyframe+empty_moov  pipe:3

clipman과의 결정적 차이

cobalt는 -c:v copy로 "손대지 않고 다시 포장"만 합니다. clipman의 쇼츠 편집(구간 자르기, 세로 9:16 크롭·스케일)은 반드시 비디오를 재인코딩해야 합니다. 즉 clipman은 cobalt가 의도적으로 피한 무거운 경로를 정면으로 다뤄야 하며, 그래서 처리를 로컬 PC에서 하는 결정이 더욱 타당합니다.

05

YouTube 추출의 현실

YouTube는 21개 서비스 중 유일하게 다른 방식을 씁니다. 그리고 cobalt가 공개 서비스에서 YouTube를 사실상 접은 이유가, clipman의 로컬 우선 전략을 정당화하는 가장 강력한 근거입니다.

  • 라이브러리: YouTube만 youtubei.js(innertube, YouTube 내부 API 클라이언트)를 사용합니다. 나머지는 HTML 안의 JSON 파싱이나 내부 REST/GraphQL 호출입니다.
  • 클라이언트·코덱: 기본 IOS 클라이언트, 코덱은 h264·av1·vp9 중 선택, 화질은 144p부터 4320p까지. 1080p 초과에서는 WEB_EMBEDDED + 세션 토큰 경로로 전환합니다.
  • 봇가드 우회: 높은 화질이나 봇 차단 상황에서는 별도 세션 서버(yt-session-generator)가 만든 poToken과 visitor_data가 필요합니다. 쿠키(cookies.json)는 선택이지만 인증이 필요한 콘텐츠에 씁니다.

clipman에 직결되는 사실

cobalt 메인테이너는 공개 인스턴스의 YouTube 지원 중단 원인을 이렇게 밝혔습니다(Issue #1356): "YouTube의 강한 네트워크 제한이 여전하고, 우리 규모(중앙 프록시 서버)에서는 이를 우회할 수 없다." 법적 조치가 아니라 대규모 중앙 서버를 겨냥한 기술적 차단입니다. clipman은 사용자 PC(가정용 IP)에서 본인 쿠키로 동작하므로 바로 그 문제를 구조적으로 회피합니다. 이것은 로컬 우선 설계의 부가 효과가 아니라 핵심 이점입니다. (분석·추론, 근거: Issue #1356 + 로컬 다운로더의 동작 방식)

06

프론트엔드

벤치마크로 삼을 부분은 UI의 절제된 단순함입니다. 메인 화면에는 입력창 하나와 마스코트, 지원 목록뿐입니다.

  • 메인은 Omnibox 하나. URL을 붙여넣는 단일 입력이 전부이고, 세부 옵션은 /settings의 10개 카테고리로 숨깁니다. clipman의 "첫 화면은 입력창 하나" 방향과 정확히 일치합니다.
  • 설정은 localStorage. 사용자 설정을 JSON으로 localStorage에 저장하고 스키마 버전 기반으로 자동 마이그레이션합니다(IndexedDB 아님).
  • 테마는 3모드. auto·light·dark. auto는 OS 선호를 실시간 감지합니다.
  • 인스턴스 선택. 웹 UI가 처리 대상 API 인스턴스를 설정에서 바꿀 수 있습니다. 프론트와 백엔드가 느슨하게 결합된 구조라 가능합니다.
  • PWA이나 오프라인은 없음. 설치형 매니페스트는 있지만 서비스워커가 없어 오프라인 캐싱은 지원하지 않습니다.

단일 라이선스가 아니라 컴포넌트별로 갈립니다. clipman이 코드를 참고할 때 반드시 알아야 할 경계입니다.

브랜딩·마스코트·이름은 어느 라이선스에도 포함되지 않는 별도 저작물이며, 개조판을 만들 때는 이름을 포함한 모든 브랜딩을 제거해야 합니다. 프로젝트는 "무책임(zero liability), 사용자 책임, 캐시 안 함, 피라시 도구가 아님"을 명시적으로 선언합니다. 브라우저 개발자도구로도 같은 콘텐츠를 받을 수 있다는 논리로 정당성을 주장합니다.

clipman 결론

cobalt의 UI 코드는 재사용 불가(비상업 + 브랜딩 제거)입니다. 참고만 하고 화면은 자체 제작해야 합니다. 다만 clipman은 개인·로컬 도구이므로 배포에 따르는 라이선스 부담 자체가 거의 발생하지 않습니다.

가장 중요한 세 가지 교훈

  • 편집이 곧 차별점임이 코드로 확정됐다. cobalt는 다운로드에 특화됐고 편집은 의도적으로(또는 미성숙으로) 비어 있습니다. clipman의 "다운로드에서 쇼츠 완성까지 한 흐름"이라는 존재 이유가 검증됐습니다.
  • 로컬 우선이 YouTube 차단을 구조적으로 피한다. cobalt가 규모 때문에 겪은 중앙 서버 차단을, 로컬 도구는 애초에 겪지 않습니다. 법적 리스크뿐 아니라 기술적 견고성 면에서도 로컬이 유리합니다.
  • cobalt의 복잡성 절반은 clipman에 불필요하다. 터널 서명, 다층 인증, Redis, 인스턴스 분리는 전부 공개 멀티유저 남용 방지용입니다. clipman은 이 절반을 걷어내고 그 예산을 편집 UX에 쓰면 됩니다(1루타 전략).

근거와 신뢰도. 이 분석은 2026년 9월 기준 imputnet/cobalt main 브랜치의 코드 원문(raw.githubusercontent.com)과 공식 문서를 1차 출처로 삼았습니다. 7개 축을 병렬 조사한 뒤 완결성 비평과 공백 보충을 거쳤고, 대부분 항목이 높은 신뢰도(코드 직접 확인)입니다. clipman 시사점은 사실이 아니라 분석·추론이며 그렇게 표시했습니다.
